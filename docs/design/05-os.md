# environments — os

Oct 4, 2026

## Lo que entendí (2026-10-04)

os tiene dos cambios grandes: un gestor de versiones personal y una modularización completa, migrando todo lo que el os actual ya hace. Lo de abajo de esta sección es el borrador anterior.

### Gestor de versiones

- Cada usuario tiene su propio historial de versiones del os, que arranca en `1.0.0`. Nexo no lo versiona; el usuario puede hacerlo si quiere.
- Cuando el usuario pide un cambio, el agente lo hace y le muestra una preview en el navegador. Si el usuario aprueba, se buildea una versión nueva.
- Numeración: cada build aprobado suma uno al último número. Cada 10, pasa a la siguiente menor: `1.0.9` → `1.1.0`.
- El os siempre arranca con el build más nuevo. Se puede volver a cualquier versión anterior.
- Un build nuevo no se carga solo. El agente no cierra el os: el os detecta la versión nueva en su carpeta y muestra "Versión nueva detectada, reiniciá la app para cargarla".

Si no aprobás la preview, el agente ajusta y vuelve a mostrarla; solo un cambio aprobado genera build.

### Modularización

- Cada sector del os es un módulo con versión propia, y cada módulo puede tener submódulos con la misma forma. Por ejemplo, el editor es un módulo y sus librerías (Monaco, LSP, terminal) son submódulos internos.
- La referencia es otro proyecto modular propio: carpeta plana por módulo, organizada por rol, con `submodules/` y un manifiesto. Adaptado a Nexo: la documentación y la lógica de negocio de cada módulo van en `context/`, no al lado del código.
- No se pierde ninguna funcionalidad del os actual: se migra y se modulariza.

```
modules/<nombre>/
├── module.json       nombre, versión, depends_on, ruta en el rail
├── server/           rutas y lógica del lado servidor
├── web/              vistas y componentes
├── tests/
└── submodules/       misma forma adentro
```

### Preguntas para cerrar

Respondidas en la charla:

- **Versión base y versiones personales.** Lo que viene del repo es la base. El código personal lo hace cada usuario: lo deja en local o lo sube como PR. Cuando el repo se actualiza, se actualiza la base.
- **Comparar e integrar.** Un botón compara versiones y un agente integra las funcionalidades que el usuario elija. Ejemplo: tu `1.0.5` + los cambios nuevos de la base = `1.0.6`.
- **Módulos autodetectados.** Como en Odoo: cada módulo tiene un archivo clave (manifiesto) y el os detecta solo todo lo que esté en `modules/`. Un gestor de módulos permite activarlos o desactivarlos, respetando las dependencias entre ellos.
- **La versión mayor es solo de Nexo.** `2.0.0` y siguientes las sacan únicamente los responsables del repo, para releases grandes. El usuario sube solo los otros dos números. Un salto de mayor hecho en local no está soportado y rompe esa versión.
- **Los cambios personales no se suben solos.** Lo instalado por npm se actualiza como una dependencia y no gestiona versiones contra el repo; lo que edites queda en local. Para contribuir, se clona el repo y se sube el cambio a mano.

También decidido, y con esto os queda cerrado:

```
os/
├── source/     copia local del código que el usuario edita
├── versions/   builds: 1.0.0, 1.0.1, … (arranca con el más nuevo)
└── data/       notas, tickets, vault: las versiones nunca lo tocan
```

## Qué es

`os/` es la carpeta del entorno `environments` donde vive agent-os, la app, ya buildeada y versionada. Está acordado que agent-os es un repo propio, con base y lógica propias, y que dentro del entorno va solo el build. Está acordado también que el entorno se instala vía una librería npm. Todo lo demás de esta página (estructura, actualización, contrato) es propuesta para charlar.

## Qué trae del v1

agent-os ya existe en el v1 y la idea es separarlo del hub, conservando su base.

| Hoy en el v1 | En environments | Qué mejora |
| --- | --- | --- |
| agent-os vive dentro del repo del hub, en `os/` | Repo propio; en `os/` queda solo el build | El hub deja de mezclar código de app con configuración |
| Se corre con `make os` / `make os-app`, con `node_modules` en el repo | Se instala ya buildeado, sin dependencias de desarrollo en el entorno | Menos peso y menos cosas que se rompen |
| Desktop con Tauri, que corre su propio server | Se mantiene como parte del build versionado | Se reutiliza lo que ya anda |
| Datos en `os/data/`, junto al código | Datos separados del build (propuesta) | Actualizar la app no pisa tus datos |
| Sin versionado del build | Versiones guardadas una al lado de otra | Se puede volver atrás si algo falla |

## Cómo se trabaja (propuesta)

La propuesta es guardar cada versión del build al lado de las otras y apuntar a una con `current`. Es un punto de partida: los detalles de versionado se definen después.

```
environments/
├── environment.config.json
├── library/
├── projects/
├── skills/
└── os/
    ├── versions/
    │   ├── 1.0.0/        (build completo)
    │   └── 1.1.0/
    ├── current -> versions/1.1.0
    └── data/             (datos de la app, fuera del build)
```

**Cómo llega una versión.** Hay dos caminos posibles: el paquete npm baja un release ya buildeado, o buildea local desde el repo de agent-os. Ver opciones abiertas.

**Actualizar.** El instalador lee `environment.config.json` para saber qué versión hay instalada. Baja la nueva a `os/versions/`, la prueba y recién ahí mueve `current`.

**Volver atrás.** Alcanza con apuntar `current` a la versión anterior, que sigue en disco. Cuántas versiones se guardan queda por definir.

**Dónde viven los datos.** En `os/data/`, separado de `versions/`. Actualizar o borrar un build nunca toca los datos de la app.

**Contrato con el entorno.** agent-os lee del entorno, pero no es dueño de nada de eso:

- `environment.config.json`: versión instalada, tools habilitados, preferencias y dónde está cada carpeta.
- `projects/`: los proyectos y sus workspaces.
- `library/`: convenciones, comandos y memoria.
- `skills/`: las skills de fábrica y las propias.

Lo que el entorno guarda, el entorno lo gobierna. agent-os solo lo muestra y lo usa.

## Opciones abiertas

Quedan tres decisiones por tomar; ninguna está resuelta.

**1. Cómo llega el build**

| Opción | Cuándo elegirla | Costo o riesgo |
| --- | --- | --- |
| El paquete npm baja un release ya buildeado (recomendado) | Querés instalar rápido y sin toolchain | Hay que publicar releases por plataforma |
| Buildeo local desde el repo de agent-os | Querés modificar la app o no dependés de releases | Pide Node y Rust instalados; instalación lenta |
| Ambos, con release por defecto y build local opcional | Querés flexibilidad desde el día uno | Dos caminos para mantener y testear |

**2. Cuántas versiones se guardan**

| Opción | Cuándo elegirla | Costo o riesgo |
| --- | --- | --- |
| Solo la actual y la anterior | Querés ocupar poco disco | Rollback limitado a un paso |
| Las últimas N configurables | Querés control sobre el espacio | Una opción más en `environment.config.json` |
| Todas hasta borrarlas a mano | Querés historial completo | El disco crece con cada update |

**3. Dónde viven los datos de la app**

| Opción | Cuándo elegirla | Costo o riesgo |
| --- | --- | --- |
| `os/data/` dentro del entorno | Querés todo junto y fácil de respaldar | Hay que cuidar que el instalador nunca lo toque |
| En `.state/`, la carpeta propuesta para logs y cache | Querés una sola carpeta de estado | Mezcla datos de la app con cache descartable |
| Fuera del entorno, en una ruta del sistema | Querés separar del todo datos y entorno | Se pierde la portabilidad de copiar una carpeta |
